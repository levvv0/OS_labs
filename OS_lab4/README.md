# Длительные работы в workqueue

Модуль ядра Linux для уровня «Hey, Not Too Rough». Реализация использует механизмы из лекции: `work_struct`, `INIT_WORK`, `container_of`, `alloc_workqueue`, `queue_work`, `msleep`, `flush_workqueue`, `destroy_workqueue`.

При загрузке создаётся собственная очередь `tsulab_queue` и пять независимых работ. Для каждой работы случайно выбираются число этапов от 2 до 5 и задержка каждого этапа от 1000 до 2000 мс. Эти параметры остаются постоянными на протяжении работы. Случайные значения разных работ могут совпадать.

Параметры очереди заданы в программе: флаг `WQ_UNBOUND` и `MAX_ACTIVE = 5`. Всего существует пять работ, поэтому одновременно могут выполняться не более пяти. Фактическое начало и порядок выполнения определяет ядро. Этапы внутри каждой работы идут последовательно; сообщения разных работ могут чередоваться.

## Сборка

Нужны компилятор C, make и заголовки запущенного ядра. На Ubuntu, если они ещё не установлены:

```bash
sudo apt update
sudo apt install build-essential linux-headers-$(uname -r)
```

В каталоге с `tsulab.c` и `Makefile`:

```bash
make
```

Результат — `tsulab.ko`. Используется современное ядро с `get_random_u32_below()`; этот интерфейс есть в ядре 7.0 из предыдущей работы.

## Проверка

Модуль называется `tsulab`, как в предыдущей лабораторной. Если предыдущий модуль ещё загружен, сначала выгрузите его командой `sudo rmmod tsulab`.

В первом терминале включите просмотр новых сообщений ядра:

```bash
sudo dmesg -w
```

Во втором терминале загрузите модуль:

```bash
time sudo insmod ./tsulab.ko
```

`time` покажет время выполнения команды загрузки. Команда должна завершиться после постановки работ, пока они ещё выполняют свои этапы. В журнале появятся строки вида:

```text
Welcome to the Tomsk State University
tsulab: queueing work 1, stages=3, delay=1400 ms
tsulab: work 1 started
tsulab: work 1, stage 1/3, sleep 1400 ms
tsulab: 5 works queued, init finished
tsulab: work 1, stage 2/3, sleep 1400 ms
```

Это пример фрагмента журнала; параметры и порядок сообщений при каждом запуске могут отличаться. Каждая строка этапа печатается перед засыпанием на выбранное время. После последнего этапа печатается `finished`.

Пока работы выполняются, запросите выгрузку:

```bash
sudo rmmod tsulab
```

Выгрузка дождётся завершения всех пяти работ, включая ожидающие запуска. В этот момент `rmmod` может несколько секунд не возвращать приглашение терминала — это ожидаемое поведение. Уже завершённые работы повторно не запускаются. В конце журнала будут пять строк `result work ...: completed .../... stages`, а затем:

```text
tsulab: all 5 works completed, queue destroyed
Tomsk State University forever!
```

Для отдельной проверки сводки после возврата `rmmod`:

```bash
sudo dmesg | tail -n 40
```

Проверить отсутствие модуля в списке загруженных:

```bash
lsmod | grep '^tsulab '
```

После выгрузки эта команда ничего не выведет. Для повторного опыта снова выполните `insmod`. Просмотр `dmesg -w` можно остановить сочетанием Ctrl+C.

## Память и завершение

Массив `items` объявлен на уровне файла, поэтому продолжает существовать после возврата `tsulab_init()`. Обработчики работают каждый со своим элементом. Параметры элемента задаются до `queue_work()` и после этого не меняются; счётчик `completed` изменяет только обработчик своей работы.

В `tsulab_init()` нет ожидания завершения работ. Засыпание через `msleep()` происходит только в обработчике workqueue и не занимает процессор непрерывным циклом.

В этой реализации выбран разрешённый заданием вариант: завершить все работы при выгрузке. `flush_workqueue()` вызывается до чтения итоговых счётчиков и удаления очереди. После него обработчики завершены, поэтому выгрузка может безопасно вывести результаты. Затем `destroy_workqueue()` уничтожает очередь. Код модуля и массив работ освобождаются ядром после возврата из функции выгрузки. Новые работы после загрузки не создаются.
